# Boehm: MCP-based Performance Testing Automation

Named after [Barry Boehm](https://en.wikipedia.org/wiki/Barry_Boehm), known for the COCOMO model and spiral model of software development.

## Goal

A Model Context Protocol (MCP) server that provides a unified control plane for performance testing tools (Tulip, k6, JMeter, Gatling, etc.), driven by AI coding agents. Includes agent orchestration patterns and opencode skills for perf testing methodology.

## Architecture

```
AI Agent (Claude Code, Cline, etc.)
  │  Loads skills (added later)
  │  Uses MCP protocol
  ▼
perf-mcp-server (Kotlin/JVM)
  ├── Core Layer
  │   ├── MCP Handler        — exposes MCP tools/resources
  │   ├── Orchestrator       — routes test plans to adapters, manages runs
  │   └── Baseline Store     — persists runs as JSON, supports baseline tagging
  └── Adapter Layer
      ├── Tulip Adapter      — in-process JVM, first-class support
      ├── k6 Adapter         — shell exec
      └── ...                — additional tool adapters
```

### Data Flow

1. Agent calls `run_test(tool, test_name, test_plan)` via MCP
2. Core layer validates, persists pending run, dispatches to adapter
3. Adapter translates test plan to tool-specific invocation
4. Adapter parses tool output into normalized `RunResult`
5. Core layer persists result, returns `run_id` to agent

## MCP Tools

| Tool | Input | Output |
|---|---|---|
| `list_adapters` | — | Adapter names + supported test types |
| `run_test` | `tool`, `test_name`, `test_plan` | `run_id`, `RunResult` |
| `get_run` | `run_id` | Full `RunResult` |
| `mark_baseline` | `tool`, `test_name`, `run_id` | Confirmation |
| `get_baseline` | `tool`, `test_name` | Baseline `RunResult` or null |
| `list_baselines` | `tool?`, `test_name?` | List of baselines |
| `compare_with_baseline` | `tool`, `test_name`, `run_id` | Diff report with deltas |
| `list_runs` | `tool?`, `test_name?`, `limit?` | Recent runs metadata |

## Adapter Interface

Every adapter implements:

```
interface PerfToolAdapter {
    val name: String
    val supportedTestTypes: List<TestType>
    fun run(testPlan: TestPlan): RunResult
    fun validate(testPlan: TestPlan): List<ValidationError>
}
```

## Future Vision

### Git Integration & PR Troubleshooting

Boehm will integrate with git to automatically detect performance regressions introduced by pull requests:

```
Tool: check_pr
Input:  repo_path, pr_number (or base + head refs), test_suite
Output: diff report linking perf changes to specific commits/code changes
```

**How it works:**
1. Agent calls `boehm check_pr(repo="/path", base="main", head="feature")`
2. Boehm stashes current state, checks out `base`, runs test suite, stores baseline
3. Checks out `head`, runs same test suite
4. Generates diff comparing head vs base
5. **Commit-level blame** — if multiple commits in the branch, Boehm can bisect-run to identify which commit introduced each regression
6. Returns report linking regressions to specific commits, files, or code changes

**CI integration:** Designed to run in GitHub Actions / GitLab CI — non-zero exit when regressions exceed threshold, with a PR comment posted containing the comparison report.

### Advanced Statistical Analysis

Beyond simple p50/p90/p99 delta comparison:

| Capability | Description |
|---|---|
| **Distribution comparison** | Compare full latency histograms (not just percentiles) using KS-test or Mann-Whitney |
| **Trend analysis** | Aggregate last N runs into a trend line; detect gradual degradation before it crosses thresholds |
| **Anomaly detection** | Flag runs that deviate statistically from the historical distribution |
| **Resource correlation** | When available, correlate perf results with CPU/memory/GC metrics from the target system |
| **Multi-variable regression** | Identify which test parameters (concurrency, payload size, etc.) most affect latency |

### Skills Expansion

| Skill | Purpose |
|---|---|
| `boehm-pr-check.md` | Guide the agent through the full PR perf review workflow |
| `boehm-trend-analysis.md` | Interpret trend data and identify gradual degradation |
| `boehm-bisect.md` | Guide the agent through git-bisect style performance regression hunting |

### Cross-Tool Comparison

Compare results from different tools running the same test scenario (e.g., same HTTP endpoint tested with Tulip, k6, and Gatling) to validate tool consistency and identify tool-specific overhead.

## Implementation Phases

### Phase 1 — MCP Server Scaffold + Tulip Adapter
- Gradle project setup with MCP SDK
- Core layer: MCP handler, orchestrator, baseline store
- Tulip adapter (in-process JVM)
- `run_test`, `get_run`, `list_adapters` tools
- Unit tests

### Phase 2 — Baseline & Comparison
- `mark_baseline`, `get_baseline`, `list_baselines`, `compare_with_baseline`, `list_runs` tools
- Baseline store implementation
- Unit tests + integration tests

### Phase 3 — Evals
- Evaluation framework for testing MCP server correctness
- Test fixtures and scenarios

### Phase 4 — Additional Adapters
- k6 adapter (shell exec)
- JMeter adapter (shell exec)

### Phase 5 — Agent Integration Patterns
- Example agent configurations
- Workflow documentation

### Phase 6 — Git PR Integration
- `check_pr` tool with automatic checkout/run/compare workflow
- Commit-level bisect for regression attribution
- CI integration (GitHub Actions, GitLab CI)

### Phase 7 — Advanced Analysis
- Statistical distribution comparison
- Trend analysis and anomaly detection
- Cross-tool comparison
- Resource correlation

## Non-Goals

- No HTML report generation (use Markdown + Mermaid)
- No cloud services or network dependencies for storage
- No embedded database — JSON files only
- No report rendering in the MCP server (handled by skills layer)
- No GUI or dashboard
